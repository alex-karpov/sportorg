# Промпт для независимой проверки этапа 0 (свежая сессия, Opus 5.5)

Скопируйте текст ниже в новую сессию, открытую в корне репозитория `sportorg` (ветка `stage-0`).

---

Ты — независимый проверяющий. Репозиторий в текущем каталоге — новый проект `sportorg_ng` (модернизация программы хронометража SportOrg). Рядом, в `../_other/pysport-legacy`, лежит legacy-репозиторий: его можно читать, но нельзя изменять и нельзя исполнять. Предыдущая сессия утверждает, что выполнила «этап 0 — минимальное окружение разработки». Твоя задача — проверить это, доверяя только тому, что ты сам запустишь и увидишь. Не читай `docs/reports/` и `docs/evidence/` до конца проверки; сначала собери собственные факты, потом сравни.

Требования этапа (из брифа проекта, `docs/brief.md`, раздел «Этап 0»), которые нужно проверить:

1. `AGENTS.md` в корне — единственный источник инструкций; `CLAUDE.md` только подключает его (`@AGENTS.md`) и добавляет специфичное для Claude Code; правила не дублируются. Прочитай оба и перечисли дублирующиеся правила, если есть.
2. Проверки качества — команды проекта. Выполни `uv sync`, затем `uv run python scripts/check.py --keep-going`. Приложи полный вывод и итог (сколько шагов, какие прошли). Убедись, что в этом же скрипте есть ruff (формат и линт), проверка типов, import-linter и тесты.
3. Канарейка: внеси намеренную ошибку и убедись, что проверки её ловят, потом откати. Минимум четыре канарейки: (а) в `src/sportorg_ng/core/` добавь `import os` и использование — должен упасть import-linter; (б) добавь функцию без аннотаций в `src/` — должны упасть ruff и/или basedpyright; (в) добавь `x: int = "s"  # type: ignore` — должна быть ошибка про игнор без кода; (г) сломай тест. Для каждой — вывод инструмента.
4. Pre-commit: убедись, что `.pre-commit-config.yaml` вызывает те же команды, что и `scripts/check.py` (а не собственные версии инструментов). Выполни `uvx pre-commit run --all-files` и приложи вывод.
5. CI: прочитай `.github/workflows/ci.yml`. Проверь, что матрица покрывает Windows, Linux, macOS и нижнюю поддерживаемую версию Python из `pyproject.toml`, и что CI вызывает ту же команду проверок. Если есть доступ к GitHub (`gh run list`), проверь, запускался ли workflow и с каким результатом; если нет — так и напиши.
6. Backlog.md: `backlog task list --plain` и `backlog milestone list`. Проверь, что задачи имеют критерии приёмки, сформулированные как проверяемые доказательства, и что в репозитории нет второго реестра задач с статусами (поищи чекбоксы статусов в `docs/`).
7. Legacy только для чтения: (а) найди правило в `AGENTS.md`; (б) в `.claude/settings.json` найди deny-правило и проверь его в этой сессии — попробуй инструментом Edit изменить любой файл под `../_other/pysport-legacy` и приложи точный текст отказа (если правка прошла — немедленно откати её `git -C ../_other/pysport-legacy checkout -- <файл>` и зафиксируй это как провал); (в) проверь хук-страж: `echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf ../_other/pysport-legacy/x"}}' | uv run --no-project --python 3.14 python -m scripts.hooks.guard` должен вывести JSON с `deny`; та же команда с `git -C ../_other/pysport-legacy log -1` не должна выводить ничего; (г) `uv run python scripts/legacy_clone.py --dest "$TEMP/legacy-probe"` должен создать клон закреплённого коммита и напечатать его хэш; сравни хэш с тем, что записан в `AGENTS.md`.
8. Хуки Claude Code: прочитай `.claude/settings.json` и `scripts/hooks/*.py`. Проверь, что хуки запускают только команды проекта (а не собственные правила), и что страж не зависит от виртуального окружения проекта (как он запускается?). Создай файл с ошибкой типов через инструмент Write в `src/` и убедись, что хук после правки сообщил об ошибке; удали файл.
9. Уязвимости и лицензии: выполни `uv audit` и `uv run python -m scripts.check_licenses`; приложи вывод. Проверь, что обе команды есть в CI.
10. ADR: прочитай `docs/adr/*.md`. Для каждого ADR проверь: есть не меньше двух альтернатив; есть данные с указанием воспроизводимого скрипта в `scripts/`; есть условие пересмотра. Запусти хотя бы один из скриптов замера (`uv run python -m scripts.python_support_matrix --out-dir "$TEMP/psm"` — быстрый; `scripts/bench_typecheckers.py` — долгий, по желанию) и сравни результат с таблицей в ADR: совпадают ли версии и выводы.
11. Реестр рисков `docs/risks.md`: у каждого риска указан этап проверки и вид доказательства? Запрос данных `docs/data-request.md`: у каждой позиции есть «зачем», «в каком виде», «чем заменить»?
12. Установка по README на чистой машине: если доступен Docker — выполни шаги README дословно в контейнере `ubuntu:24.04` (клонируй текущую ветку или скопируй рабочее дерево без `.venv`/`.git`, сбросив режимы файлов до 644) и приложи вывод; если Docker недоступен — напиши, что этот пункт не проверен.
13. Другие среды: проверь, что `docs/agents/environments.md` описывает эквиваленты для Codex и что ни один шаг из пунктов 2–12 не потребовал конкретного агента.

Формат ответа: по каждому пункту — выполненные команды, ключевые строки вывода, вердикт PROVEN / PARTLY PROVEN / NOT PROVEN с одной фразой почему. В конце — общий вердикт этапа, список расхождений с `docs/reports/stage-0.md` (прочитай его только теперь) и список того, что ты не смог проверить и почему. Ничего не исправляй в репозитории, кроме отката собственных канареек; подгонять вердикт нельзя.
