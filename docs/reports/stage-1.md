# Отчёт по этапу 1: археология legacy

Дата: 2026-10-25. Ветка `stage-1` от `main` 170a28a. Сессия Claude Code в WSL2 (Opus 5.5): план, общий модуль, приёмка, ручные проверки и этот отчёт. Направления W1–W6 делали субагенты Sonnet 5.5 двумя партиями по три.

Объект: закреплённые коммиты `pysport@b548c35` и `templates@cd95382` (`legacy.toml`). Legacy только читался, через git по закреплённому коммиту, и не запускался. После каждого направления `scripts.legacy verify` печатал `ok`.

Каждое число ниже получено скриптом из `scripts/archaeology/`. Команды лежат в `commands.txt` рядом с выводом, а для каждого числа ещё и в промпте проверки `docs/reports/stage-1-verification-prompt.md`. Ручные классификации лежат в файлах `*.manual.md`, их критерии указаны в начале каждого файла.

## Вердикт этапа: PROVEN по шести критериям TASK-7, с ограничениями

**Что доказано в этой сессии:**
- Все шесть критериев приёмки TASK-7 закрыты evidence (таблица ниже).
- Каждое направление перезапущено при приёмке, выводы совпали байт в байт.
- У каждого направления выборку из 10 тегов `file:line` я сверил с исходником глазами. Всего скрипт проверил 2872 уникальных тега во всём evidence и ни одной проблемы не нашёл.
- Классификатор дефектов проверен вручную на 50 коммитах.
- Мёртвый код проверен вручную на 30 находках.
- Вручную классифицированы все 686 находок по ОС и по российской специфике в ядре.

**Что не доказано и почему:** в разделе «Что не доказано». Главное:
- поведение legacy (на этом этапе его не запускали);
- соответствие разрядов ЕВСК действующей редакции (нужен документ правил);
- полнота правила дефектов: оценка ≈ 69 %, 95 %-интервал 40–95 %.

Правило 3 AGENTS.md требует повторить проверку этапа в свежей сессии. Для этого подготовлен промпт с командой на каждое число и с канарейками.

## Главные находки

**Структура** (`structure/`):
- **Горячие точки.** Топ-3 по формуле «коммиты × сложность»: `models/memory.py` (218 коммитов × 666 = 145 188), `gui/main_window.py` (31 920), `gui/menu/actions.py` (22 098). Корреляция числа коммитов со сложностью ρ = 0,64.
- **Нарушения слоёв.**
  - Подавляющее большинство в `sportorg/libs`: 13 импортов из `libs` в `common`, `models`, `utils` и `language`. То есть `libs` — не чужой вендоренный код, а код проекта (вопрос В3).
  - Вне `libs` три импорта вверх на уровне модулей и один локальный: `settings.py:257` импортирует прикладной слой.
  - import-linter с контрактом `layers` нашёл те же 16 пар модулей.
- **Импорт по строке.** Действия меню вызываются по имени класса, а базовый класс диалогов вызывает методы по шаблону имени: `getattr(self, f"convert_{id}")` и т. п. [код: pysport@b548c35 sportorg/gui/dialogs/dialog.py:172-343]. Статические инструменты такие зависимости не видят (новый риск R17).
- **Мёртвый код.** Сырая точность vulture 40 %, с флагом `name_in_string` 58 % (`structure/dead-code-sample.manual.md`). По-настоящему мёртвый код есть, например `OpenRecentAction`, `set_bibs`, два метода `reconnect`, недостижимая ветка в sportiduino.
- **Namespace-пакет.** `sportorg/modules/recovery` — каталог без `__init__.py`. grimp и import-linter его не видят, свой разбор через `ast` видит.

**Зависимости** (`dependencies/`):
- **Состав.** Runtime: 59 версий (41 имя). Extras `gui` и `win`: 10 версий. Dev: 54 версии. 41 версия нужна только под маркер Python 3.8.
- **Лицензии.**
  - `sportident` 1.2.8 — runtime-зависимость с классификатором `Other/Proprietary License` (расхождение Р2).
  - У семейства PySide6 6.6.3.1 вердикт «неизвестно»: классификаторы LGPL и проприетарный.
  - Крейт `unicode-ident` требует лицензию `Unicode-3.0`, которой нет в allowlist.
- **Уязвимости.** 227 записей OSV на 22 версиях пакетов, 209 из них в runtime. Больше всего у aiohttp: 74 и 72 записи на двух версиях. Свой клиент OSV, `uv audit` и osv-scanner сошлись на всех записях. У Rust 4 записи, все у `pyo3` 0.28.3.

**История дефектов** (`defects/`):
- **Классы.** Больше всего дефектов в классах `ui` (35) и `other` (50). Дальше import-export 15, device 14, calc 13, report-print 12, persistence 10, online 9.
- **Доля исправлений по модулям.** Выше всего у `libs/sfr` (21,7 %), `modules/backup` (20,5 %), `libs/ocad` (20,0 %).
- **Почему `other` такой большой.** В таблице путей нет `memory.py` без ключевого слова и нет старой структуры `sportorg/app/*`. На это приходится большинство расхождений по классу в ручной выборке (вопрос В5).
- **Issues и PR.** 46 issues и 532 PR. По меткам классифицировать почти нельзя: только `github_actions` и `dependencies` указывают на класс.

**Форматы и протоколы** (`formats/`):
- **Кодировки.** cp1251 у CSV WinOrient и OCAD, UTF-8 у IOF, UTF-8-SIG с автоопределением через `chardet` в `utils/text.py`.
- **Последовательный порт.** Все адреса портов — переменные: перебор `COM0–31` или `/dev/ttyUSB*`.
- **Устройства только на чтение.** У SPORTident serial нет «читателя» на уровне модуля проекта: обмен идёт внутри библиотеки `sportident`. У SFR HID нет «писателя».
- **Файл соревнования.** Читается и пишется через `modules/backup` и `actions.py`, а не через `memory.py`.

**ОС и российская специфика** (`os-ru/classification.manual.md`):
- **В ядре нет кода под конкретную ОС.**
- **Только под Windows, без запасного пути:**
  - считыватель SFR (pywinusb);
  - считыватель Impinj RFID: pyImpinj стоит только под Python 3.8;
  - открытие сохранённого .docx-отчёта через `os.startfile` (расхождение Р1);
  - сборка установщика.
- **Только под Windows, но с запасным путём:** прямая печать сплитов через win32print, в остальных ОС печать идёт через HTML.
- **Автопоиск порта sportiduino** работает в Windows и Linux. На macOS нужно указать порт явно: в пять категорий это не укладывается.
- **Российская специфика в ядре** — один блок: шкала разрядов `Qualification` с таблицами и присвоением разрядов (76 находок), плюс умолчания `ru_RU` и `windows-1251` (6 находок).

**Инструменты** (ADR-0007, `tools/`):
- **Сложность функций — ruff C901.** Уже стоит в проекте. Ранжирование функций совпадает с radon и lizard: ρ ≈ 0,90.
- **Граф импортов — свой разбор через `ast`, grimp для перекрёстной проверки.**
- **Мёртвый код — vulture**, находки читаются только вместе с флагом `name_in_string`.
- **Новые dev-зависимости:** `vulture` и `grimp`.
- **Не подошли:**
  - skylos не работает в песочнице: Python 3.14 запускает процессы через forkserver, а ему нужен AF_UNIX-сокет;
  - deadcode падает на 3.14: `ast.Str` удалён;
  - semgrep не выпускает колёса для 3.15.

## Что не доказано и почему

- **Поведение legacy.** На этапе 1 legacy не запускался: устройства, печать, ОС и производительность оценены только по коду. Категории ОС в ручной классификации описывают пути кода, а не запуски на трёх ОС.
- **Разряды.** Соответствие разрядов ЕВСК и правил присвоения действующей редакции требует документа правил, пока это `[допущение]` до этапа 3.
- **Ручные проверки.** Их делал один человек, выборки небольшие: 30 находок мёртвого кода (погрешность около ±15 п. п.) и 50 коммитов. Полнота правила дефектов оценена с поправкой на выборку: ≈ 69 %, 95 %-интервал 40–95 %.
- **Канарейки** проверяют скрипты, которые читают legacy по закреплённому коммиту: гипотезы, дефекты, инвентарь. `structure.py` запускает ruff и vulture по рабочему дереву `.legacy`, поэтому канарейка с данными к нему не применима. Его проверяют повторный запуск и тесты.
- **Меню.** Описана только статическая часть. При запуске меню фильтруется по ключам `show` и `feature`, а плагины добавляют свои пункты.
- **Уязвимости.** Записи OSV на дату кэша 2026-10-25. Достижимость уязвимого кода не оценивалась.

## Ход работы и инциденты

- **Маскировка личных данных в W6.** В первой версии выводов W6 оказались имена людей из тестовых фикстур legacy («Иван», «Добрынин Сергей» и др.). Я заметил это при приёмке до коммита.
