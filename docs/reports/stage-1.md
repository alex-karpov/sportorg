# Отчёт по этапу 1: археология legacy

Дата: 2026-10-25. Ветка `stage-1` от `main` 170a28a. Сессия Claude Code в WSL2 (Opus 5.5): план, общий модуль, приёмка, выборочные проверки, классификация находок и этот отчёт. Выборочные проверки и классификацию делал агент основной сессии, человек их не проверял. Направления W1–W6 делали субагенты Sonnet 5.5 двумя партиями по три.

Объект: закреплённые коммиты `pysport@b548c35` и `templates@cd95382` (`legacy.toml`). Legacy только читался, через git по закреплённому коммиту, и не запускался. После каждого направления `scripts.legacy verify` печатал `ok`.

Каждое число ниже получено скриптом из `scripts/archaeology/`. Команды лежат в `commands.txt` рядом с выводом, а для каждого числа ещё и в промпте проверки `docs/reports/stage-1-verification-prompt.md`. Суждения агента (выборочные проверки, классификация, разбор лицензий) лежат в файлах `*.agent.md`, их критерии указаны в начале каждого файла. Это не вывод скриптов, и человек их не проверял.

## Вердикт этапа: PROVEN по шести критериям TASK-7, с ограничениями

**Что доказано в этой сессии:**
- Все шесть критериев приёмки TASK-7 закрыты evidence (таблица ниже).
- Каждое направление перезапущено при приёмке, выводы совпали байт в байт.
- У каждого направления выборку из 10 тегов `file:line` агент сверил с исходником. Всего скрипт проверил 2901 уникальный тег во всём evidence и ни одной проблемы не нашёл.
- Классификатор дефектов агент проверил выборочно дважды, по 50 коммитов. Вторая выборка взята после изменения классификатора по решению В5.
- Мёртвый код агент проверил выборочно, 30 находок.
- Все 686 находок по ОС и по российской специфике в ядре классифицировал агент. Это не выборка.
- Человек эти суждения не проверял.
- Свежая сессия агента повторила проверку этапа по промпту (правило 3) и воспроизвела все числа байт в байт. Её замечания разобраны в разделе «Независимая проверка».

**Что не доказано и почему:** в разделе «Что не доказано». Главное:
- поведение legacy (на этом этапе его не запускали);
- соответствие разрядов ЕВСК действующей редакции (нужен документ правил);
- полнота правила дефектов: по второй выборке ≈ 52 %, 95 %-интервал 27–83 %.

Правило 3 AGENTS.md требует повторить проверку этапа в свежей сессии. Для этого подготовлен промпт с командой на каждое число и с канарейками.

## Главные находки

**Структура** (`structure/`):
- **Горячие точки.** Топ-3 по формуле «коммиты × сложность»: `models/memory.py` (218 коммитов × 666 = 145 188), `gui/main_window.py` (31 920), `gui/menu/actions.py` (22 098). Корреляция числа коммитов со сложностью ρ = 0,64.
- **Нарушения слоёв.**
  - **До решения В3** было V1 17, V2 13, V3 12. Большинство приходилось на `sportorg/libs`: 13 импортов из `libs` в `common`, `models`, `utils` и `language`.
  - **После решения В3** `sportorg/libs` разделён по ролям:
    - адаптеры устройств и сервисов и кодеки ввода-вывода — ранг 3;
    - `wdb_online_sender_dialog` — ui;
    - чистые разборщики остались на ранге 0;
    - вид V2 убран.
  - **V1, 4 нарушения:**
    - три импорта из прикладного слоя в GUI: печать, `sportident/result_generation.py`, `winorient/wdb_number_setter.py`;
    - один локальный импорт: `settings.py:257` импортирует прикладной слой.
  - **V3, 3 нарушения:** фундамент импортирует библиотеки GUI и звука. `utils/time.py` импортирует Qt (PySide2 и PySide6), `common/audio.py` — playsound3.
  - import-linter с контрактом `layers` нашёл те же 4 пары модулей.
- **Импорт по строке.** Действия меню вызываются по имени класса, а базовый класс диалогов вызывает методы по шаблону имени: `getattr(self, f"convert_{id}")` и т. п. [код: pysport@b548c35 sportorg/gui/dialogs/dialog.py:172-343]. Статические инструменты такие зависимости не видят (новый риск R17).
- **Мёртвый код.** Сырая точность vulture 40 %, с флагом `name_in_string` 58 % (выборочная проверка агентом, `structure/dead-code-sample-check.agent.md`). По-настоящему мёртвый код есть, например `OpenRecentAction`, `set_bibs`, два метода `reconnect`, недостижимая ветка в sportiduino. `WdbOnlineSenderDialog` к приложению не подключён ни разу. Это отдельный скрипт отправки онлайн-результатов с зашитым адресом события; без запроса его не переносить (статус в том же файле).
- **Namespace-пакет.** `sportorg/modules/recovery` — каталог без `__init__.py`. grimp и import-linter его не видят, свой разбор через `ast` видит.

**Зависимости** (`dependencies/`):
- **Состав.** Runtime: 59 версий (41 имя). Extras `gui` и `win`: 10 версий. Dev: 54 версии. 41 версия нужна только под маркер Python 3.8.
- **Лицензии.**
  - `sportident` 1.2.8 — runtime-зависимость с классификатором `Other/Proprietary License` (расхождение Р2). По первоисточникам лицензия — GPL-3.0-or-later. Классификатор поставил сборщик poetry-core, а не автор (`dependencies/licence-sources.agent.md`).
  - У семейства PySide6 вердикт «неизвестно» только у версии 6.6.3.1. Она нужна только под Python 3.8. У 6.10.0 лицензия `LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only`.
  - Крейт `unicode-ident` требует лицензию `Unicode-3.0`. FSF считает её совместимой с GPL, но в allowlist её нет. Пока в проекте нет Rust, это ни на что не влияет.
- **Уязвимости.** 227 записей OSV на 22 версиях пакетов, 209 из них в runtime. Больше всего у aiohttp: 74 и 72 записи на двух версиях. Свой клиент OSV, `uv audit` и osv-scanner сошлись на всех записях. У Rust 4 записи, все у `pyo3` 0.28.3.

**История дефектов** (`defects/`):
- **Классификатор расширен по решению В5.**
  - Старая структура `sportorg/app/*` переводится в `sportorg/*`.
  - Класс правок `memory.py` определяется по изменённым функциям.
  - Класс 168 дефектов продукта теперь решают: путь — 62, ключевое слово — 58, функции `memory.py` — 4, остаток `other` — 44 (было 50).
- **Классы.** Больше всего дефектов в классах `ui` (37) и `other` (44). Дальше device 16, calc 15, import-export 15, report-print 12, persistence 10, online 9.
- **Доля исправлений по модулям.** Среди модулей хотя бы с 10 коммитами без слияний выше всего у `libs/sfr` (21,7 %), `modules/backup` (17,7 %) и `modules/live` (17,3 %).
- **Выборочная проверка агентом на новой выборке** (`defects/sample-check-2.agent.md`, seed 20261026):
  - «исправление или нет»: совпадение 90 %, точность 96 %;
  - полнота ≈ 52 % (27–83 %), по обеим выборкам ≈ 60 % (38–82 %). Интервалы учитывают неопределённость и точности, и доли пропусков; три общих коммита выборок посчитаны один раз;
  - класс совпал в 9 из 24 случаев (38 %). Это единственная независимая оценка класса.
- **Где класс расходится:** шаблоны в старом каталоге `templates/`, файлы 2017 года в корне, `memory.py` без ключевого слова, ложные срабатывания ключевых слов («report», «time», «read»).
- **Вывод:** таблица «модуль × класс» — грубый ориентир, класс отдельного коммита ненадёжен.
- **Issues и PR.** 46 issues и 532 PR. По меткам классифицировать почти нельзя: только `github_actions` и `dependencies` указывают на класс.

**Форматы и протоколы** (`formats/`):
- **Кодировки.** cp1251 у CSV WinOrient и OCAD, UTF-8 у IOF, UTF-8-SIG с автоопределением через `chardet` в `utils/text.py`.
- **Последовательный порт.** Все адреса портов — переменные: перебор `COM0–31` или `/dev/ttyUSB*`.
- **Устройства только на чтение.** У SPORTident serial нет «читателя» на уровне модуля проекта: обмен идёт внутри библиотеки `sportident`. У SFR HID нет «писателя».
- **Файл соревнования.** Читается и пишется через `modules/backup` и `actions.py`, а не через `memory.py`.
- **Табло результатов SFR (`.srb`).** При каждом сохранении, если включена настройка, рядом пишется файл `.srb`: строки с разделителем табуляции [код: pysport@b548c35 sportorg/modules/backup/file.py:71-76] [код: pysport@b548c35 sportorg/modules/backup/sfr_results_board.py:8]. Первая версия таблицы `formats/` его пропускала (см. «Независимая проверка»).

**ОС и российская специфика** (`os-ru/classification.agent.md`):
- **В ядре нет кода под конкретную ОС.**
- **Только под Windows, без запасного пути:**
  - считыватель SFR (pywinusb);
  - считыватель Impinj RFID: pyImpinj стоит только под Python 3.8. «Только Windows» здесь держится на инструкции установки и CI (`--extra win` только для Windows [код: pysport@b548c35 CONTRIBUTING.md:38]), а не на коде: колесо pyImpinj универсальное;
  - открытие сохранённого .docx-отчёта через `os.startfile` (расхождение Р1);
  - сборка установщика.
- **Только под Windows, но с запасным путём:** прямая печать сплитов через win32print, в остальных ОС печать идёт через HTML-шаблоны. Пункт «Internal printing» диалог предлагает на всех ОС, и вне Windows он, по коду, ломает печать сплитов (расхождение Р8).
- **Автопоиск порта sportiduino** работает в Windows и Linux. На macOS нужно указать порт явно: в пять категорий это не укладывается.
- **Российская специфика в ядре** — один блок: шкала разрядов `Qualification` с таблицами и присвоением разрядов (76 находок), плюс умолчания `ru_RU` и `windows-1251` (6 находок).

**Инструменты** (ADR-0007, `tools/`):
- **Сложность функций — ruff C901.** Уже стоит в проекте. Ранжирование функций совпадает с radon и lizard: ρ ≈ 0,90.
- **Граф импортов — свой разбор через `ast`, grimp для перекрёстной проверки.**
- **Мёртвый код — vulture**, находки читаются только вместе с флагом `name_in_string`.
- **Новые dev-зависимости:** `vulture` и `grimp`.
- **Не подошли:**
  - skylos не работает в песочнице: Python 3.14 запускает процессы через forkserver, а ему нужен AF_UNIX-сокет;
  - deadcode падает на 3.14: `ast.Str` удалён;
  - semgrep не выпускает колёса для 3.15.

## Что не доказано и почему

- **Поведение legacy.** На этапе 1 legacy не запускался: устройства, печать, ОС и производительность оценены только по коду. Категории ОС в классификации агента описывают пути кода, а не запуски на трёх ОС.
- **Разряды.** Соответствие разрядов ЕВСК и правил присвоения действующей редакции требует документа правил, пока это `[допущение]` до этапа 3.
- **Выборочные проверки и классификация агентом.**
  - Их делал один агент, основная сессия. Человек их не проверял.
  - Выборки небольшие: 30 находок мёртвого кода (погрешность около ±15 п. п.) и 2 × 50 коммитов.
  - Полнота правила дефектов оценена с поправкой на выборку: ≈ 52 % (95 %-интервал 27–83 %), по обеим выборкам ≈ 60 % (38–82 %).
  - Класс отдельного коммита совпадает с меткой агента в 38 % случаев. Это оценка по независимой выборке. 79 % на первой выборке не в счёт: на ней классификатор настраивали.
  - Категории O8 и O19 опираются на чтение кода и инструкции установки, а не на запуск.
- **Форматы.** Таблица `formats/` видит запись и чтение через файловый объект-параметр только при именах `file`, `f`, `fp`, `fh`, `fd`, `fobj`, `stream`. Формат такой строки задаёт вызывающий код, сама строка его не называет. Методы объектов с другими именами пропускаются.
- **Лицензии.** Строки «review session» в `licence-sources.agent.md` агент основной сессии не перепроверял. Независимая проверка сверила их офлайн по хешам загрузок. Данные GitHub API, происхождение копий страниц gnu.org, FSF и SPDX и версия списка SPDX остались непроверенными.
- **Канарейки** проверяют скрипты, которые читают legacy по закреплённому коммиту: гипотезы, дефекты, инвентарь. `structure.py` запускает ruff и vulture по рабочему дереву `.legacy`, поэтому канарейка с данными к нему не применима. Его проверяют повторный запуск и тесты.
- **Меню.** Описана только статическая часть. При запуске меню фильтруется по ключам `show` и `feature`, а плагины добавляют свои пункты.
- **Уязвимости.** Записи OSV на дату кэша 2026-10-25. Достижимость уязвимого кода не оценивалась.
